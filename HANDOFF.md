## Objective and bounded deliverable

Establish the **durable precondition for local incremental maintenance**: when one source or host owner becomes dirty, retain the authenticated old source summary and an unknown-impact ticket *before* the old root/head can be lost; then close that ticket to an exact known impact only after the new selected source state and complete same-session host/referrer fan-out have been proved. The output is a persisted, read-only **impact certificate** suitable for the next C2-S3 ordered-index/CAS implementation. It must not make queries ready or retire tickets merely because the impact set is known. This is a meaningful storage/authority slice, not another in-memory helper or faster whole-catalog bootstrap.

Implement the smallest coherent ownership change needed across `SourceRepository`, the acquisition/host capability and discovery. If the existing source-head write cannot atomically select the new root in this slice, use an explicit durable repair/unknown-impact record in the same activation transaction. The retained old root may remain physically present for repair, but public discovery must still return non-ready while any relevant authority is unclosed. Do not make a stale root queryable by suppressing global host/head checks. SourceId, NodeId, physical path and semantic path must remain distinct; host structural owners and source owners must remain separate.

For one changed source A, prove the following exact lifecycle in code and tests:

1. **Clean → unknown dirty:** persist an owner-specific, incarnation-fenced ticket and the original authenticated old summary/head/root identity before any mutation can invalidate their selection. Missing/corrupt old proof, unsaved source, overlap with another writer, or exhausted budget must be explicitly non-ready. Unknown new keys can affect any negative; do not infer a narrowed impact from old keys.
2. **Prepare:** acquire the new source once using S1's four-family summary path (deletion with authoritative absence uses zero source-family visits). Keep the old/new delta private and copied. Capture the exact host transition and resolver referrers, structural participants, Date/non-Date and Daily Notes effects that can change third-party bindings. Use canonical host capabilities; no duplicate parser/resolver, policy classifier or graph traversal. If those inputs cannot be completely observed, the ticket stays unknown.
3. **Unknown → known:** persist a versioned impact record bound to old/new selected source heads, original summary commitment, ticket, root, and complete host transition. Include the conservative union of direct old/new keys and actual third-party host/referrer keys/owners. A known impact is not a graph certificate, selected index root or durable ticket retirement. Newer overlapping mutations supersede it; a repeated repair cannot silently erase a newer unknown.
4. **Interruption and recovery:** a crash at every await/staging/activation boundary leaves either the old clean selection or an explicit durable unknown/known repair state. Cross-connection readers must never observe a clean old root with a new head, or infer absence from an incomplete impact. Reopening the database must recover the ticket without replaying every unchanged owner merely to discover what changed. Reclamation must respect active leases; no wall-clock expiry of authority.

**Scope boundary:** do not implement the ordered authenticated copy-on-write membership/owner trees, local root publish, query disjoint-continuity path or semantic graph publication in this transfer; those form C2-S3 after S2's journal/impact certificate is accepted. Do not claim that C is queryable yet. C3 still owns fresh-session validation, long exact IDs, hot-range continuation, terminal consumers. Do not change GraphIndex/settings/UI, source/body/graph formats or semantic policy. A database version bump is required if you add or change stores/indexes; make it additive and prove existing durable data survives. If the old v6 derivative format must be retired, reject it explicitly rather than resetting accepted data.

## Concrete adversarial oracle and acceptance tests

- **A adds B:** At clean root R, A lacks a B link. After A adds `Friends:: [[B]]`, a B-negative query cannot reuse R. The durable unknown ticket exists before the head transition; the eventual known impact contains B even though B was absent from A's old keys. An unrelated C must be *excluded from the known impact only when actual host/referrer closure proves that*, not from direct key disjointness alone. A separate scenario where C contains `[[Alias]]` and A changes alias resolution must include C despite no direct A→C key.
- **Mutation forms:** cover edit with unchanged key set but new head, create, rename across different SourceIds, deletion with disk-only/masked head, recreate at the same SourceId, concurrent/coalesced edits, and a host-only topology/resolution/Daily Notes change. Verify C1's retained-body/tombstone/retry behavior remains intact.
- **Durability/faults:** real IndexedDB tests with two connections for stale ticket/head/root CAS, interrupted write at each meaningful stage, quota/write rejection, eviction, reopen/recovery and source/body/graph record preservation. Reuse the actual database and production repository; test-only catalog ports alone are insufficient. Corrupt or missing old summary, changed host stamp, cancellation and demand loss must leave conservative authority. No ready prefix, dropped ticket or unbounded retry.
- **Work accounting:** instrument source-family visits, Markdown reads/parses, selected heads, relevant host calls and page/transaction reads/writes for one edit and deletion in a fixture with many unrelated owners. S2 is allowed to leave queries pending; its journal/impact preparation must be local and must never replay all unchanged source families. Separate arithmetic models from measurements, include memory/page caps and explicit backpressure behavior.
- **Compatibility/oracle:** keep full-compiler equality, declaration multiplicity/provenance and existing five-policy oracle strict. Preserve existing v5 source/body/graph bytes and the already-created v6 database on migration. No synthetic time sleeps for completion; use repository flush/transaction fences.

Run available `npm run verify`, `npm run test:sources`, `npm run test:sources:browser`, `npm run build`, and `git diff --check` with actual versions, recording failures/skips and environmental limits. Do not modify a timing bound, golden or host fixture to make a check green.
