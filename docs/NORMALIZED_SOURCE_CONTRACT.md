# Normalized source contract (C11, SI2 accepted)

C11 introduced the host-free input vocabulary; C12 supplied the host adapters, C13 the portable parser/compiler, and C14 the shared source-patch path. **SI2 is accepted:** property references are now acquired independently of ontology/image settings. `GraphBuilder` still owns Obsidian acquisition and publication staging; `core/graph/compiler.ts`, the evidence store and resolver remain the only semantic interpretation path. `GraphIndex`, scheduling, search and storage keep their existing owners.

The runtime contract is `src/core/graph/source.ts`. Raw facts carry no ontology role, configured assignment label, image-selector flag, inference direction, `RelationType` or inverse declaration. `core/graph/sourcePolicy.ts` interprets neutral references before any source/target graph materialization in both full compilation and patch preparation. SI2 does not itself persist the fact stream. The separate SI3 storage implementation is **Accepted**; settings-triggered semantic rebuild removal remains unimplemented SI4 work.

## SI3 storage companion — Accepted

[Source repository](SOURCE_REPOSITORY.md) defines a separate strict on-disk vocabulary rather than mechanically persisting current host-selected SI2 targets. Lexical value/payload/candidate frames retain every distinct spelling before host destination deduplication. Host resolution/counts and Date facts have a separately replaceable family. The accepted compiler-facing SI2 protocol, its finality and selector semantics remain unchanged. Finite immutable inline parser inputs share payloads with provenance; arbitrary frontmatter values and semantic settings are not mirrored. Per-file patches acquire even on a semantic no-op; complete builds may reuse neutral bodies on a legacy-cache miss while independent inventory persists source heads after publication. Synchronous graph publication remains outside IndexedDB.

### Existing collisions and exclusions that must survive collection

- A host-resolved ordinary link can point to the same target as a frontmatter/inline ontology occurrence. Both inputs must survive; defined/inferred meaning is resolved later.
- Conflicting frontmatter and body ontology occurrences remain separate records with their original property/value/location. C11 does not suppress the body occurrence.
- Multiple inline declarations for the same pair remain separate occurrences. The compatibility fixture contains duplicate/conflicting declarations intentionally.
- Hidden assignments interpret the same neutral facts. The compiler excludes self-links and treats hidden evidence as directional; selection is not part of physical source identity. The retired index-file exclusion is not reintroduced.
- Reverse relationship evidence is virtual and remains compiler-owned; a producer must not emit an extra inverse source occurrence.
- Image selection uses the same neutral reference candidates, not configured presentation records. Image decoding, resource URLs and node imagery stay out of semantic persistence.
- `url-origin` is derived from successfully parsed body URL origins; malformed URLs keep their raw URL node and omit origin evidence. A shared URL has one URL identity and one derived origin relation, while every declaring note keeps its own `body-url` occurrence/referrer.

## Identity, resolution and provenance

`NodeId` remains opaque. `SourceEntityRef` carries `id`, `kind`, materialization `state`, optional `semanticPath` and optional `physicalPath` as independent facts. A producer may therefore represent case-distinct paths with different IDs, an unresolved semantic target without a file, a deleted/pathless identity, or an ID whose text has no relationship to a path.

`SourceRecordBase.contribution` identifies a physical per-note contribution when it differs from the semantic declaring node. For example, tag membership declares tag→note but is withdrawn/recomputed with the member note. C12 producers must populate this owner/revision for those facts; tag hierarchy itself remains structural. This does not prescribe persistence or change current withdrawal algorithms.

Entity state has four explicit values:

- `materialized`: the coherent read contains the semantic entity (a host file when that kind has one);
- `unresolved`: a semantic target identity exists but no backing entity resolves for this declaration;
- `missing`: the producer has no entity for the identity in this coherent read (distinct from a deliberate unresolved placeholder);
- `deleted`: a newer source revision says a previously observed identity was removed.

`SourceTargetRef` keeps the raw declared target/subpath apart from the exact entity chosen by the producer. This is the contract for ambiguous names, headings/subpaths, source-relative Obsidian resolution, case-distinct paths and links to records that arrive in a later batch. The Obsidian adapter is responsible for `getFirstLinkpathDest`/metadata-cache semantics. Portable core must not add a global basename/case rule.

`SourceProvenance.definition` preserves the existing evidence/property definition label when the producer already exposes one. A neutral `reference-value` header retains the exact physical `fieldName` and a `normalizedFieldName` lookup key, neither of which is a relationship role. SI2 removes the historical `configuredFieldName` from raw provenance: configured assignment labels, role-group multiplicity and configured ordering belong to the shared policy selector and selected evidence, not to the producer.

Metadata/property provenance includes its frontmatter/inline/body/host surface where available. Preserve competing note-type/primary-tag values rather than selecting frontmatter precedence in a source producer. `field-name` facts preserve current discovery inputs without carrying unrelated values.

Physical source location is similarly independent. Inline ontology can carry one-based line plus zero-based character range. Body URLs currently have line information and the fixture producer supplies a verified range. Frontmatter provenance currently has the property and raw value but production does not own a reliable body character range for it. Resolved/unresolved host link maps are aggregate source→target counts; C11 therefore does not invent per-link locations for those summaries.

## SI2 physical reference frames and canonical selection

The historical `ontologySourceCollector.ts` module now exports `ObsidianReferenceSourceCollector(host, runtime, file, metadata)` with no settings parameter. It borrows the merged input and uses `iteratePropertyValueSteps()` / `iterateReferenceScanSteps()` from `core/parser/referenceValues.ts`. Scalar scanning delegates to the established `iterateLinkReferencesFromValue()` grammar. Plain strings are not guessed to be note links. Host-relative destination resolution remains in the adapter; the core never applies basename or path heuristics.

Each eligible value emits, in order:

1. One `reference-value` header: opaque source/revision-scoped `valueId`, exact and normalized field names, frontmatter/inline surface, policy-independent physical ordinal, origin, and available syntax/location.
2. Ordered `reference-payload` chunks: the original top-level string or the JSON representation of the whole nested value, serialized **once**. Chunk index and final marker are validated independently of batch finality.
3. Ordered `reference-candidate` records referring to that value: unique target ordinal, lexical target/subpath separate from `SourceTargetRef.entity`, and exact host resolved-link count. The last candidate carries `final: true`, independently proving that the candidate sequence was not truncated. Deduplication is by resolved target identity **within one whole value**, including a nested frontmatter list/object. Separate physical values preserve multiplicity.

`inlineMapIndex` records an observation, not current image policy. Matching physical occurrences and the established inline-value map share one value. An exceptional map-only/mismatching value has `origin: inline-map`, no invented location and no ontology occurrence; it remains eligible for map-based image reconciliation. This preserves accepted cached-input distinctions. Property-name discovery is still a separate producer and retains empty/non-reference fields without their arbitrary values.

`ReferencePolicySelector` captures the seven configured role groups and image fields once. Distinct exact configured labels with equivalent normalized keys remain distinct, as do exact duplicate assignments. `ReferenceSourcePolicyRead` validates value, payload and candidate ordering plus both terminal markers, then selects candidates **before** `compiler.consumeReference()` or the patch entity-read callback can see their endpoints. Dormant candidates create neither source nor target nodes, ghosts, URLs, declarations, ownership nor missing-target rebuild demand. A separate structural/host/body fact may independently activate that same entity; dormancy is not an exclusion rule.

Selected ontology values join their explanation payload once and share it across resulting evidence. Dormant and image-only payload chunks are checked then discarded. The last retained value is released on completion or compiler rejection. The compiler restores the accepted configured-label, frontmatter-before-inline, physical-value, target and duplicate-assignment order by cooperatively ordering **existing private evidence buckets**. Temporary per-evidence order keys are dropped before publication; there is no candidate replay array, second graph or shadow production compiler. Original evidence IDs, multiplicity, configured frontmatter labels, physical inline labels and canonical resolver precedence remain intact.

Image selection counts one visual target per original value. Only generic `obsidian-link` declarations are suppressed when the captured host count is positive and no larger than the selected visual count. A prose occurrence beyond those values retains the generic link; explicit ontology evidence remains even when its field is also an image field. Existing selected-image target materialization is retained; dormant images do not materialize.

## Bounded iteration and validity

A normalized read is a sequence of `NormalizedSourceBatch` objects, each limited to **256 records** by the contract. A dense single Markdown file is allowed to span as many batches as necessary; there is intentionally no `FileContribution.occurrences[]` container that can become a hidden unbounded full-file/full-vault allocation. The repeated `source` + `sourceRevision` and, where different, `contribution` owner/revision supply later contribution keys if measurement justifies persistence. **The 256-record cap alone is not a byte bound.** The SI2 reference producer additionally flushes at 256 KiB of estimated retained record bytes and limits each raw payload chunk to 16,384 UTF-16 code units. It serializes no whole-frontmatter mirror and retains only a per-value deduplication set, one output queue and small scan state. A single indivisible lexical identity record (an unusually long field/path/target) can exceed the estimate and travels alone; strings are never truncated. The estimate is not a measured heap bound. One selected raw value still needs its full explanation string once; nested parser input and one synchronous scalar regex/host resolution remain inherited limits. No SI5 memory/latency claim is made.

The producer owns two different revision concepts:

1. `SourceRevision` is the opaque revision of one declaring source. An Obsidian adapter may include mtime/size in how it constructs the token, but mtime alone is not asserted to be a complete host revision guarantee.
2. `SourceReadBoundary` contains an opaque collection generation and coherent snapshot revision for the whole read.

Within one coherent boundary, `sequence` is the batch validity/ordering token: batch content cannot be revised in place. If a producer observes changed content, replacement or deletion, it must mint a new generation/snapshot boundary rather than reuse a sequence number from the old read. `acceptSourceBatch()` is only a contract-seam validator. It accepts sequential batches from one boundary and rejects mixed boundaries, sequence gaps, batches after finality and oversized batches. `sourceReadCanPublish()` becomes true only after a final batch **and** only if the adapter still reports the same generation/snapshot boundary. For **selected** materialized references, a producer must supply complete entity facts before finality (and explicit unresolved/missing/deleted state for absent endpoints). An early batch may reference an exact target identity whose `entity` fact appears later. The cursor checks only sequence/boundary/finality, **not record contents or entity completeness**; `sourceReadCanPublish()` is a necessary stream-validity condition, not sufficient proof that a compiler result is valid. C12 producers/C13 compiler must enforce completion before graph publication, without assuming batch-local target order. Fixture tests verify endpoint fact completion, including Date placeholders. Replacement/deletion during collection must mint a newer boundary; the older complete stream is stale and cannot publish.

C11 does not define how Obsidian captures a coherent boundary or schedule/retry work. C12 must capture the host facts; C14/C15 later own latest-wins compilation/publication/demand coordination. The create/delete-during-build observation recorded during C10 remains a C14/C15 validation case rather than being hidden inside these records.

## Historical C12 adoption path

C12 migrated one source family at a time into the existing authoritative `GraphBuilder` path:

1. C12a: file/container/tag entities and hierarchy facts, with exact before/after graph/evidence equality;
2. C12b: resolved/unresolved host link summaries and frontmatter/inline ontology occurrences, retaining one classifier/resolver — accepted production adapters in full and incremental paths; C12b validation records main-agent/native evidence;
3. C12c: Date, body URL/origin, presentation-link reconciliation, graph-relevant metadata and discovery facts — accepted in full and cooperative incremental compilation.

At every slice, normalized records should be consumed incrementally/batch-wise rather than retained as a second whole-vault DTO array. Parser pools, persisted semantic shards, delta logs, incremental publication and secondary-index redesign remain assigned to C13–C17 as documented in `docs/INDEXING_ARCHITECTURE.md`.


## C12c completeness and retained host seams

Full and incremental compilation use `ObsidianMetadataSourceCollector` with metadata, relation and discovery-only families. Date registry/Daily Notes/Moment remain in `createObsidianMetadataSourceHost`; the SI2 reference adapter owns field-reference resolution, including potential image references. Body URL records retain declaring-note occurrences and optional origins; the compiler owns origin evidence and lifetime. Each neutral reference candidate carries `hostOccurrenceCount` obtained only for that source/target; selection decides whether to use it. Full compilation retains lightweight private visual/host pair counts until final suppression; the shared per-source compiler retains per-note counts until reconciliation; there is no duplicate whole-vault resolved-link map.

Inline semantic and visual values come from the established `inlineFields` map, while discovery comes from physical occurrence names. These surfaces can differ in accepted cached inputs; the collector must not silently substitute one for the other or invent positions for map-owned values. Aliases/tags remain string facts. Configured note-type/primary-tag values use plain scalar/array projections; unsupported object/nested entries carry `{unsupported: true}` without retaining their contents or host instances. The non-null marker preserves legacy frontmatter precedence: an unsupported frontmatter object blocks inline fallback and unwraps to no note type. Null/undefined still allow the existing nullish fallback. Other arbitrary property values never cross as semantic metadata.

## SI2 fingerprint and validation boundary

`index/SourceFingerprint.ts` streams version-3 compact topology/provenance equality tokens. Reference-bearing values participate regardless of current ontology/image fields. Each original raw value is hashed once, not per target or again in the location lane. Independent non-reference fields are ignored; text inside a reference-bearing value is retained explanation context, so changing that context legitimately changes equality. Aliases/tags, finite note-type/primary-tag compatibility inputs and host Date/link/body-URL observations remain inputs. Moving an inline location without changing its value affects provenance, not topology.

Production hashes cooperatively by accumulated character/scan work, not one awaited Promise per tiny token. Both full and patch paths retain their source/file revision checks after hashing and before synchronous publication. SI2 itself changed no schema/store/startup-restore path. The separate accepted SI3 companion adds version-5 source storage and restart acquisition reuse while keeping saved graph snapshots under their existing signature policy. Settings-only reinterpretation is still **not implemented**.

`reference-policy.test.mjs` directly exercises production collection, full/patch replay, dormancy before entity lookup, configuration ordering/multiplicity/conflicts, exact image suppression, dense shared payloads, cancellation, frame finality and neutral fingerprints. `settingsIndependence.mjs` additionally tests actual GraphBuilder fingerprints under changed ontology/image settings. Accepted graph/evidence/search goldens remain unchanged. Exact dependency, browser, build and native-host checks passed for SI2; see the [acceptance report](validation/settings-independent-indexing-si2-2026-09-29.md). Exported repositories may omit `tests/fixtures/normalized-source/Assets/picture.png`; restore that real fixture before running its source-relative image oracle, rather than weakening the expected result.
