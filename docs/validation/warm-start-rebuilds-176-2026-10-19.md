## Ordered output and input analysis

Outside observation, existing `startupCacheIdentity` streams full persisted
records, preserving order and duplicate multiplicity. Before/after restart,
active generation, ordered pages/evidence, policy/configuration, source sequence
**8105**, source heads and saved semantic inputs are identical. This is record
equality, not a new reuse proof. Native host replay enumeration changes across
reload, despite unchanged files/settings; do not label that input identical.

An additional **untimed oracle**, using actual canonical compilation/save on the
post-reload host, compares complete records against the saved graph. Same page
membership and 215/1,568 counts do **not** establish equivalence:

- Page/evidence encounter order differs; 43 pages have differing relation arrays.
- Eight relation definition-label fields change ordering (`next, previous` versus
  `previous, next`, or `friend, related` versus `related, friend`). These are
  observable strings, not an ignorable sorted representation.
- Policy/discovered fields and other persisted page fields match. This fixture
  shows no changed first alias, but does not negate the shared-URL preferred-label
  hazard demonstrated in #165. Evidence multisets match only as a secondary
  diagnostic; exact ordered comparison remains failed.

Thus no count/fingerprint shortcut, sorted-evidence comparison or silent compiler
reordering is introduced. The oracle is separate from the warm-run zero-build/
zero-save counts; its requested build/save cost is not hidden in those results.
